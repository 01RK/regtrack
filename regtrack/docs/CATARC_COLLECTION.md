# 标准自动采集与消息中心（v24-cloud.1）

## 消息规则

| 栏目 | 采集时的处理 | 消息操作 |
|---|---|---|
| 计划下达 | 未建档：等待追踪决定；已有预研档案：自动推进立项；已有立项或更后阶段、归档：跳过 | 新计划「确认追踪」后按立项建档，或「本次忽略」；自动立项消息点击「我已知悉」 |
| 征求意见更新 | 只匹配系统已有、未归档且阶段较早的标准，立即推进征求意见 | 点击「我已知悉」 |
| 标准公告更新 | 只匹配系统已有、未归档且阶段较早的标准，立即推进发布，同步正式标准号、发布日期、实施日期，保留计划号 | 点击「我已知悉」 |
| 全部动态 | 所有采集变化与处理记录；异常也保存在这里 | 尚未处理的事项仍可逐条操作 |

三个分类页只列出未处理事项；点击「我已知悉」才标为已读并从分类页移除，保留在全部动态中。打开页面、切换标签页、查看来源、再次采集均不会自动知悉。知悉一条不影响其他消息。无批量已读接口、按钮或未读动态标签页。采集成功或无变化不会生成消息，结果仅在设置中显示。

新计划确认后创建 PROJECT_APPROVAL 主档与初始历史记录，计划号与正式标准号分开保存。已有预研档案在采集时直接推进 PROJECT_APPROVAL 并生成待知悉消息。确认期间若已有同名档案，则合并并保留更后阶段，不重复建档；归档档案须先恢复。

新计划「本次忽略」仅对本次有效；下次采集再次发现时原消息重新待确认并标为未读，不新增重复行。尚待确认的新计划、未知悉的自动更新不会重复堆积；已经完成的阶段不会再次推进或提醒。每条消息保存通知日期、来源、前后阶段及知悉人和时间。团队共享处理结果，重复确认返回冲突。

右上角铃铛进入「消息中心」卡片首页（/notifications），数字表示尚未处理的消息条数，零时隐藏。目前一张「最新标准进度」卡片汇总待处理数与三类数量，点击进入 /notifications/standards；详情页可返回消息中心。未来新增消息板块可在首页并列放置独立入口卡片。

标准进度消息采用紧凑行式布局，类别、标题、状态和编号／通知日期按列对齐；右侧固定为主操作、辅助操作和来源详情三列。确认追踪与我已知悉使用相同主操作位置、宽度，本次忽略与标准档案使用同一辅助列，来源链接与时间保持对齐。窄窗口将操作区移至内容下方。

## 采集设置

默认启用，每天北京时间 09:00，空库默认通知范围 7 天，演示库默认 60 天。每隔 1–365 天运行，时间可设为 HH:MM。范围下拉框提供当天、近 3 天、近 7 天，并在展开菜单内输入自定义整数天数（1–3650）后按 Enter 或点击使用，选定后直接显示「近 N 天」，无外置输入框。此控件复用项目已安装的 Tom Select dropdown_input 与 create 能力。

保存后生效；「立即采集」使用已保存配置。运行概况默认只显示下次采集、最近成功和最近结果；采集范围、起止时间及错误放在可展开的运行详情中。云服务器上的 RegTrack 服务需持续运行且联网；停机时暂停，恢复后按中断补采设置处理遗漏时段。唯一调度器每 30 秒检查，持久任务租约用于异常退出后的恢复，租约 5 分钟后过期。

## 服务器中断补采

设置中的「服务器中断补采（推荐开启）」默认开启。服务器恢复启动时，将启动记录持久化到 crawler_startup，并查找 crawler_run 中最近一次完整成功（succeeded）的采集记录。若该记录覆盖日期早于今天，就把从该日期到今天标为待补采；启用定时采集时立即排队执行，不必等正常采集时间。

- 补采包含上一次成功覆盖日期当天，以覆盖那次采集结束后才上线的同日通知。三个栏目使用同一补采范围。
- 实际范围取常规配置与待补采范围的并集。因此常规只采当天，仍能补到停机期间；常规已设 60 天，也不会因中断补采而缩小为几天。
- 本功能只在恢复启动自检时建立补采窗口，不改变常规「近 1 天＝今天」的含义，也不把所有定时执行都改为累计补采。
- 全部栏目和标准处理均无错误才记为完整成功，并清除已经覆盖的待补采时段。部分失败、任务失去执行锁或断电均不推进完整成功记录。待补采窗口保留，之后手动采集或下一次定时采集继续补；不循环高频重试。
- 断电留下的 running 日志在新任务取得执行锁后记为 interrupted，不伪造断电时间。正常退出写入 stopped_at。启动、采集范围、开始／完成时间、状态和结果均持久化在共享数据库中；不依赖控制台文本日志。
- 补采沿用现有匹配、自动更新、逐条知悉、忽略重提与去重规则。遗漏动态生成正常消息，已处理的相同进展不会再次推送，不额外生成“补采完成”消息。
- 关闭补采选项会清除待补采窗口，此后仅按配置范围采集。关闭定时采集不会自动运行，但手动采集可执行已保留的补采范围。首次安装没有完整成功记录时按常规范围执行，不推测更早历史。
- 设置状态区展示最近成功时间；待补采时段会直接提示，实际采集／补采范围在运行详情中查看。

Current recovery tests: `python -m pytest regtrack/codes/test_collection_recovery.py -q` from the repository root. See [TESTING.md](TESTING.md).

## 网站与匹配

- [计划通知](https://zxd.catarc.org.cn/zxd/portal/jhxdtz)、[征求意见](https://zxd.catarc.org.cn/zxd/portal/zqyj)、[标准公告](https://zxd.catarc.org.cn/zxd/portal/bzgg)统一按通知详情页的发布日期筛选，范围包含今天。遇到首条过期通知就停止该栏目，不解析其标准表格或继续访问其子页、后续通知、下一页。采集间隔大于范围时页面提示可能漏采。
- 范围内提取通知全部标准，立项访问子页补充 TC/WG、起草单位等信息。优先按计划号或标准号匹配，其次按唯一完整中文名匹配，统一全半角、空白及破折号。名称匹配不唯一时报错；不做模糊匹配。名称匹配的公告早于主档最早阶段日期时跳过，避免旧版本推进新项目。
- 自动更新只推进到立项、征求意见或发布，不回退、更不自动实施。每项更新与对应消息在同一事务提交；阶段历史带通知来源和自动采集署名。发布时写入实际发布日期与实施日期。
- 消息来源指向具体标准详情：立项 planDetail、征求意见项目详情（批次和项目参数）、发布 stdDetail；无独立详情则指向具体通知页。
- 单项失败回滚并继续其他标准；网络或结构错误保存在运行结果及异常消息中，相同连续错误不重复提醒。应用内消息不会发送外部邮件或即时消息。

## 云服务器启动与证书诊断

唯一运行入口为 `codes/run.py`，由部署文档中的 systemd 服务托管。不要用 `flask run`，它不启动采集调度器。所有浏览器共享服务器采集结果；用户关闭浏览器不会停止采集。设置页关闭定时采集时不会自动联网，仍可手动采集。

HTTPS 证书失败发生在网页解析前。采集使用 truststore 从服务器操作系统获取企业信任链，并保留 Requests 的代理与 CA bundle 支持；不会关闭证书校验。

在相同服务账号和网络环境中执行 `python codes/check_catarc.py`，可诊断三个来源；此命令只读取网站，不写业务数据。执行方法见 DEPLOYMENT_ZH.md 的 systemd-run 示例。

如企业网关检查 HTTPS，请让 IT 为 Linux 服务环境安装企业根证书和中间证书，或在 `/etc/regtrack/regtrack.env` 中设置 `REQUESTS_CA_BUNDLE=/etc/regtrack/company-ca.pem`。证书文件必须允许 regtrack 服务账号读取。修改后重启服务。修复证书不需要重建数据库。

代理可通过服务环境中的 HTTPS_PROXY 与 NO_PROXY 配置。NO_PROXY 应含 127.0.0.1,localhost，保证同机健康检查直连；Requests 不自动读取浏览器 PAC。对外 CATARC 连接仍需要有效的代理与信任链。

本地 TLS 回归覆盖真实握手、错误证书和错误主机名；最终仍需在目标云服务器执行联网诊断。

参考：[truststore 文档](https://truststore.readthedocs.io/)、[Requests 高级用法](https://requests.readthedocs.io/en/latest/user/advanced/)。
